## Scope and method

This axis answers one question: whether a module-forward Omnigent deployment in vanixiets should be shaped as plain NixOS modules (O1) or as one clan service module with `server` and `host` roles (O2), and what each shape costs relative to the existing `openclaw` and `hermes-agent` clan services.
It also determines whether the pinned clan-core can emit Darwin configuration for `stibnite` from a clan service.
Files were read directly and line numbers were confirmed with `grep -n` and `awk` against the working tree, or with `git show` against the pinned clan-core commit.
Seven read-only `nix eval` commands were run to confirm attribute paths named in the options section; their output is quoted where used.
This note was first drafted in an earlier session of the same axis and then re-verified line by line in this session: all 107 distinct `github:` citations in the draft were resolved with `git cat-file -e` and their cited lines re-read, one misstatement about the openclaw generators was corrected (section 2), sections 5, 6, and 7 gained the findings marked as additions, and the 130 distinct citations in the final text were resolved the same way.
No `clan` command, no `just check-fast`, no deployment, no secret generation, no branch switch, and no commit was run.
Both options are described without choosing between them.

## 1. Existing clan service module shape

Vanixiets has exactly two self-hosted clan services, `openclaw` and `hermes-agent`, each in its own directory `modules/clan/services/<name>/` with a `flake-module.nix` and a `README.md` (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/services/openclaw/flake-module.nix:1`, `github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/services/hermes-agent/flake-module.nix:1`).
`nix eval .#clan.modules --apply builtins.attrNames --json` on the working tree returned `["hermes-agent","openclaw"]`, confirming those two are the whole self-hosted set.
Neither `modules/clan/`, `modules/clan/services/`, nor `modules/clan/inventory/` has its own `README.md`; the nearest enclosing README is `modules/README.md`, which says every `.nix` file under `modules/` is a flake-parts module discovered by `import-tree` with no registration step, and that a file must be git-tracked before a flake build can see it (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/README.md:8-13`).
A clan service is therefore a flake-parts module that assigns `clan.modules.<name>` rather than `flake.modules.nixos.<name>` (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/services/openclaw/flake-module.nix:3`, `github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/services/hermes-agent/flake-module.nix:3`).
Both services declare `_class = "clan.service"` and `manifest.name` (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/services/openclaw/flake-module.nix:6-7`, `github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/services/hermes-agent/flake-module.nix:6-8`).
Both define a single role named `default` with an `interface` function that declares `options` and a `perInstance` function that receives `settings` and returns `nixosModule` (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/services/openclaw/flake-module.nix:12-19,110-113`, `github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/services/hermes-agent/flake-module.nix:15-18,124-127`).
Neither service defines `darwinModule` or `perMachine`; `grep -rn darwinModule modules/clan/` matches only two comments in the sshd inventory file, not any service definition (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/inventory/services/sshd.nix:15,20`).
The pinned clan-core service machinery that these files target passes `instanceName`, `roles`, `exports`, `meta`, `machine = { name; roles; }`, `settings`, and `extendSettings` to each `perInstance` function, evaluating it once per instance per machine (`github:clan-lol/clan-core@1c21a2388ffbf9a957a60f58d18757420666cc43:lib/inventory/distributed-service/service-module.nix:670-705`).
The `perInstance` result accepts `nixosModule` and `darwinModule`, both `deferredModule` with default `{ }`, and the option documentation warns that the module is produced once per instance and that unit names should concatenate service name and instance name to stay unique (`github:clan-lol/clan-core@1c21a2388ffbf9a957a60f58d18757420666cc43:lib/inventory/distributed-service/service-module.nix:606-661`).
A separate `perMachine` function is evaluated once per machine, receives `machine` and `instances` but no `settings`, and likewise returns `nixosModule` and `darwinModule` (`github:clan-lol/clan-core@1c21a2388ffbf9a957a60f58d18757420666cc43:lib/inventory/distributed-service/service-module.nix:714-745,779-822`).
For each machine the final result is one `nixosModule` importing the `perMachine` module plus every per-instance `nixosModule`, and one `darwinModule` importing the `perMachine` module plus every per-instance `darwinModule` (`github:clan-lol/clan-core@1c21a2388ffbf9a957a60f58d18757420666cc43:lib/inventory/distributed-service/service-module.nix:1162-1176`).

## 2. OpenClaw service shape

OpenClaw's README describes the `default` role as running the openclaw gateway on the assigned machine (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/services/openclaw/README.md:1-8`).
The role interface begins with an `enable` option and continues through homeserver, bot name, Matrix server name, port, bind mode, listen addresses, hostname, service user, gateway mode, a Matrix password generator name, and config overrides (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/services/openclaw/flake-module.nix:15-107`).
The `perInstance.nixosModule` reads its package as `config.services.openclaw.package` (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/services/openclaw/flake-module.nix:121`).
That option is declared inside the per-instance NixOS module itself as `options.services.openclaw.package = lib.mkOption { type = lib.types.package; default = pkgs.openclaw-gateway; ... }`, a hand-written package option rather than `lib.mkPackageOption` (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/services/openclaw/flake-module.nix:234-239`).
Because the option is declared in a per-instance module, a second `openclaw` instance assigned to the same machine would declare `services.openclaw.package` twice; the service is single-instance by construction.
All four generators are declared under fixed names, `clawdbot-gateway-token`, `clawdbot-claude-oauth`, `clawdbot-zai-coding-api`, and `matrix-password-clawd` (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/services/openclaw/flake-module.nix:245,256,270,331`).
Only the consumption of the Matrix password path is indirected through `settings.matrixBotPasswordGenerator`, which the inventory sets to the literal `"matrix-password-clawd"` so that it matches the fixed declaration (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/services/openclaw/flake-module.nix:187-188`, `github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/inventory/services/openclaw.nix:20`).
The whole `config` block of the emitted module is wrapped in `lib.mkIf settings.enable`, while the `options.services.openclaw.package` declaration sits outside that guard (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/services/openclaw/flake-module.nix:234,241`).
The emitted NixOS module authors its own `systemd.services."openclaw-gateway"` and `systemd.services."openclaw-register-clawd"` units and a Caddy virtual host keyed on `settings.hostName` (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/services/openclaw/flake-module.nix:289,345,414`).
Its inventory instance sets `module.name = "openclaw"`, `module.input = "self"`, and assigns `roles.default.machines."cinnabar"` with a settings block whose leading comment records that `enable` is currently false and the instance is retained for a later removal phase (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/inventory/services/openclaw.nix:2-12`).
`nix eval .#clan.inventory.instances.openclaw.roles.default.machines --apply builtins.attrNames --json` on the working tree returned `["cinnabar"]`, confirming the `.#clan.inventory.instances.<instance>.roles.<role>.machines` attribute path evaluates.

## 3. Hermes-agent service shape

Hermes-agent's README states it is a clan-service wrapper around the upstream NousResearch NixOS module that imports `inputs.hermes-agent.nixosModules.default` and adapts clan-vars secrets to the upstream `services.hermes-agent.environmentFiles` option (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/services/hermes-agent/README.md:1-8`).
Its `manifest.description` repeats the same layering statement (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/services/hermes-agent/flake-module.nix:8`).
The `default` role's interface exposes `serviceUser`, `openrouterApiKeyGenerator`, `matrixBotPasswordGenerator`, Matrix names and homeserver URL, gateway and dashboard ports, allowlist, home room settings, and config overrides (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/services/hermes-agent/flake-module.nix:15-121`).
The `perInstance.nixosModule` imports the upstream module, sets `services.hermes-agent`, and forces `environmentFiles` to the clan vars paths (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/services/hermes-agent/flake-module.nix:124-127,166,175,270`).
Package ownership is delegated to the upstream module's `services.hermes-agent.package`; the wrapper reads `config.services.hermes-agent.package` for its dashboard unit and declares no package option of its own (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/services/hermes-agent/flake-module.nix:453`).
Both generator names come from role settings, `clan.core.vars.generators.${settings.openrouterApiKeyGenerator}` and `clan.core.vars.generators.${settings.matrixBotPasswordGenerator}` (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/services/hermes-agent/flake-module.nix:344,360`).
The wrapper adds `serviceConfig` hardening, `path`, and `LD_LIBRARY_PATH` to the upstream unit and authors a sibling `systemd.services.hermes-agent-dashboard` unit (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/services/hermes-agent/flake-module.nix:396,420-421,432`).
Its inventory instance sets `module.name = "hermes-agent"`, `module.input = "self"`, and assigns `roles.default.machines."cinnabar"` with settings including `serviceUser = "cameron"` and the two generator names (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/inventory/services/hermes-agent.nix:2-12`).

## 4. Clan service registration and machine-role assignment

Vanixiets imports `inputs.clan-core.flakeModules.default` in `modules/clan/core.nix` (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/core.nix:1-7`).
`clan.machines` registers `magnetite` and `pyrite` by importing `config.flake.modules.nixos."machines/nixos/<name>"` and registers `stibnite` by importing `config.flake.modules.darwin."machines/darwin/stibnite"` (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/machines.nix:3,20-21,24-25,32-33`).
The inventory records `magnetite` with `machineClass = "nixos"` and tags `nixos`, `cloud`, `hetzner`, `peer`; `pyrite` with `machineClass = "nixos"` and tags `nixos`, `laptop`, `peer`; and `stibnite` with `machineClass = "darwin"` and tags `darwin`, `workstation`, `laptop`, `controller` (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/inventory/machines.nix:65-75,77-86,99-108`).
A self-hosted service is bound through `clan.inventory.instances.<instance>.module = { name = "<service>"; input = "self"; }` (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/inventory/services/openclaw.nix:2-6`, `github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/inventory/services/hermes-agent.nix:2-6`).
Pinned clan-core resolves `module.input` by looking the string up in `flakeInputs` and taking that flake's `clan.modules` attribute, so `input = "self"` resolves to this flake's own `clan.modules.<name>` (`github:clan-lol/clan-core@1c21a2388ffbf9a957a60f58d18757420666cc43:lib/resolve-module/default.nix:29-40`).
Roles are populated either by explicit machine names, `roles.<role>.machines."<machine>" = { settings = ...; }`, or by tags, `roles.<role>.tags."<tag>" = { }`; the sshd instance uses `roles.server.tags."nixos"` and `roles.client.tags."nixos"`, and the zerotier instance uses `roles.peer.tags."peer"` (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/inventory/services/sshd.nix:16,21`, `github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/inventory/services/zerotier.nix:24`).
Pinned clan-core documents three automatic tags, `all`, `nixos` (every machine with `machineClass = "nixos"`), and `darwin` (every machine with `machineClass = "darwin"`), and permits mixing tags and machine names in one role (`github:clan-lol/clan-core@1c21a2388ffbf9a957a60f58d18757420666cc43:docs/src/guides/services/intro-to-services-revised.md:126-136`).
For every inventory machine, pinned clan-core folds all services into `machineImports`, the list of each service's final `nixosModule` for that machine, and `darwinImports`, the list of each service's final `darwinModule` for that machine (`github:clan-lol/clan-core@1c21a2388ffbf9a957a60f58d18757420666cc43:modules/clan/distributed-services.nix:152-163`).
The machine module then imports `machineImports` when the module `_class` is `nixos` and `darwinImports` when it is `darwin`, and it throws if nixpkgs is too old to supply `_class` (`github:clan-lol/clan-core@1c21a2388ffbf9a957a60f58d18757420666cc43:modules/clan/module.nix:183-192,210-217`).
At the pinned revision, the built-in `wireguard` clan service defines `darwinModule` for its `peer` role, its `controller` role, and `perMachine`, which is direct evidence that the Darwin path is exercised by a shipped service (`github:clan-lol/clan-core@1c21a2388ffbf9a957a60f58d18757420666cc43:clanServices/wireguard/default.nix:187,318,410,570,763`).
The built-in `sshd` service does not define `darwinModule`, which is why vanixiets restricts both sshd roles to the `nixos` tag and replicates CA trust in a separate Darwin module (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/inventory/services/sshd.nix:15-21`, `github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/darwin/ssh-ca-trust.nix:1-4`).

## 5. Plain NixOS module pattern for magnetite services

A plain service module is a flake-parts file assigning `flake.modules.nixos.<name>` to a NixOS module function (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/nixos/kanidm.nix:38`, `github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/nixos/matrix.nix:60`, `github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/nixos/sso-gateway.nix:45`, `github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/nixos/omnigraph.nix:3`).
The magnetite machine module binds `flakeModules = config.flake.modules.nixos` and imports service modules by bare name in a `with flakeModules; [ ... ]` list that currently includes `kanidm`, `matrix`, `sso-gateway`, and `omnigraph` (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/machines/nixos/magnetite/default.nix:7,39-57`).
Pyrite uses the identical binding and list shape with `base`, `hm-sops-bridge`, and `ssh-known-hosts` (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/machines/nixos/pyrite/default.nix:8,25-28`).
Two option styles coexist among magnetite's plain modules.
`kanidm` and `matrix` are unconditional: `kanidm.nix` declares no `enable` and no package option, hardcodes `services.kanidm.package = pkgs.kanidmWithSecretProvisioning_1_11`, and declares its three generators inline (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/nixos/kanidm.nix:58,77,106,124`).
`sso-gateway` and `omnigraph` are option-gated: `sso-gateway` declares `options.sso.enable = lib.mkEnableOption ...` and `omnigraph` declares `options.services.omnigraph.enable` and `package = lib.mkPackageOption pkgs "omnigraph" { }` (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/nixos/sso-gateway.nix:193-194`, `github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/nixos/omnigraph.nix:209-212`).
`omnigraph` is the only plain module in this set that uses `lib.mkPackageOption`, so it is the repository-native precedent for the charter's package-ownership rule (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/nixos/omnigraph.nix:212`).
Machine-level enablement of an option-gated module happens in the machine file: magnetite sets `services.omnigraph = { enable = true; ... }` and points `environmentFile` and `bearerTokensFile` at generator paths (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/machines/nixos/magnetite/default.nix:381-397`).
Those two omnigraph generators, `omnigraph-r2` and `omnigraph-bearer-tokens`, are declared in the machine file rather than in `omnigraph.nix`, so generator ownership varies by module in the existing tree (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/machines/nixos/magnetite/default.nix:328,368`).
The ingress and database idioms a server module would reuse are `services.nginx.virtualHosts.${domain}` with `enableACME = true`, `forceSSL = true`, and `proxyWebsockets = true` (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/nixos/kanidm.nix:280-293`), and `services.postgresql.ensureDatabases` plus `ensureUsers` with `ensureDBOwnership = true` merged into the shared instance (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/nixos/matrix.nix:364-370`).
The SSO gateway header states that a service with built-in OIDC should register a direct per-service kanidm client and bypass the gateway, which is the case for Omnigent (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/nixos/sso-gateway.nix:18-23`).

Addition: no README under `modules/` states when a clan service module is preferred over a plain NixOS module.
`git grep -i 'clan service'` over every `README.md` at the pinned revision matches only the two service READMEs' own titles, and `modules/README.md` describes `clan/` only as "clan inventory, services, and machine registration" (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/README.md:20`).
The one place at `main` that states a preference is the Buzz self-hosting note: "Use the plain deferred-module pattern `flake.modules.nixos.buzz-relay` rather than a clan service." followed by "Every service on magnetite uses that pattern, including the Gitea being replaced, and the clan inventory layer is statically evaluated with no `config.*` visibility, a cost this repository already pays and documents at `modules/clan/inventory/services/hermes-agent.nix:14-20`." (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:docs/notes/development/buzz/self-hosting.md:282-284`).
The inventory comment it points to reads "The clan inventory layer is pure-static (no `config.*` visibility), so the port is duplicated here as a literal rather than derived from config.services.matrix-tuwunel.settings.global.port." (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/inventory/services/hermes-agent.nix:14-20`).
The openclaw interface documents the same cost for `listenAddresses`, which are "Passed explicitly by the inventory so the host's VPN listen addresses are an explicit coupling rather than a hidden host dependency" (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/services/openclaw/flake-module.nix:65-72`).
The Buzz note is a working note dated by its last commit to 2026-08-04 and is not a README, so this axis records it as the nearest written preference rather than as a rule (Q6).
The deployment plan on the plan branch already names `modules/nixos/omnigent.nix` as `flake.modules.nixos.omnigent` and `modules/nixos/omnigent-host.nix` as `flake.modules.nixos.omnigent-host`, with magnetite importing both from `flakeModules` (`docs/notes/development/omnigent/deployment-plan.md:179-182`).

## 6. Darwin and Home Manager precedent for `stibnite`

Stibnite's machine module is `flake.modules.darwin."machines/darwin/stibnite"`, binds `flakeModules = config.flake.modules.darwin`, and imports `ssh-ca-trust`, `colima`, `dnscrypt-proxy`, and others by bare name (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/machines/darwin/stibnite/default.nix:27-46`).
A repository-native Darwin module is a flake-parts file assigning `flake.modules.darwin.<name>` (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/darwin/colima.nix:3`).

## 7. Buzz-flake module architecture

Buzz-flake exports three module surfaces from one `flake.nix`: `nixosModules.buzz-server` (aliased as `nixosModules.default`), `homeModules.buzz-agents`, and `clan.modules.buzz` (`github:fosskar/buzz-flake@6811fbd9bce5a4ec4889d2e6eb48fa75d1a7f4c7:flake.nix:57-64`).
The NixOS module declares `options.services.buzz-server.enable` and a hand-written `package` option defaulting to `self.packages.${system}.buzz-relay`, not `lib.mkPackageOption` (`github:fosskar/buzz-flake@6811fbd9bce5a4ec4889d2e6eb48fa75d1a7f4c7:modules/buzz-server.nix:42-50`).
The clan service declares `_class = "clan.service"`, a `manifest` with `name = "buzz"` and a README read from `buzz-clan.md`, and a `server` role whose interface begins with `relayUrl` (`github:fosskar/buzz-flake@6811fbd9bce5a4ec4889d2e6eb48fa75d1a7f4c7:modules/buzz-clan.nix:4-20`).
The `server` role's `perInstance` takes `instanceName` and `settings`, and its `nixosModule` imports `self.nixosModules.buzz-server`, so the clan role is a thin adapter over the flake's own plain NixOS module (`github:fosskar/buzz-flake@6811fbd9bce5a4ec4889d2e6eb48fa75d1a7f4c7:modules/buzz-clan.nix:154-172`).
Its generator is named `buzz-server-${instanceName}`, which is the instance-scoped naming the clan-core option documentation recommends (`github:fosskar/buzz-flake@6811fbd9bce5a4ec4889d2e6eb48fa75d1a7f4c7:modules/buzz-clan.nix:168-174`).
The adapter then sets `services.buzz-server = { enable = true; ... }` by forwarding role settings and pointing `environmentFile` at the generator's file (`github:fosskar/buzz-flake@6811fbd9bce5a4ec4889d2e6eb48fa75d1a7f4c7:modules/buzz-clan.nix:232-259`).
A second role, `client`, takes `roles` in `perInstance`, derives `relayUrl` from `(lib.head (lib.attrValues roles.server.machines)).settings.relayUrl`, asserts exactly one server machine, and installs a wrapped desktop package (`github:fosskar/buzz-flake@6811fbd9bce5a4ec4889d2e6eb48fa75d1a7f4c7:modules/buzz-clan.nix:264-299`).
This is the only two-role precedent among the sources read, and it shows a consumer role reading the server role's settings through the `roles` argument rather than through a duplicated instance-level option.
The clan README shows the inventory shape, `roles.server.machines.relay.settings = { relayUrl = ...; }` and `roles.client.tags = [ "workstation" ]` (`github:fosskar/buzz-flake@6811fbd9bce5a4ec4889d2e6eb48fa75d1a7f4c7:modules/buzz-clan.md:11-23`).
The Home Manager module `services.buzz-agents` owns its own `package` option and emits one `systemd.user.services.buzz-agent-<name>` per enabled agent, with no launchd branch (`github:fosskar/buzz-flake@6811fbd9bce5a4ec4889d2e6eb48fa75d1a7f4c7:modules/buzz-agents.nix:115-120,140-144`).
The sibling buzz-flake note already records that buzz-flake ships no TLS, OIDC, or sandbox integration, so those remain vanixiets-side concerns in either option (`docs/notes/development/omnigent/research/buzz-flake.md:144-174`).

Instance settings for the server URL.
The task names an instance-level server URL; in pinned clan-core, settings live on roles, either as `roles.<role>.settings` shared by every machine in the role or as `roles.<role>.machines.<machine>.settings` per machine (`github:clan-lol/clan-core@1c21a2388ffbf9a957a60f58d18757420666cc43:lib/inventory/distributed-service/service-module.nix:86-91,189-235`).
Two realizations fit: the `server` role's interface declares `domain` (so the URL is `https://${settings.domain}`) and the `host` role's `perInstance` reads it from `roles.server.machines` exactly as buzz-flake's `client` role reads `relayUrl`, with an assertion that exactly one server machine exists (`github:fosskar/buzz-flake@6811fbd9bce5a4ec4889d2e6eb48fa75d1a7f4c7:modules/buzz-clan.nix:264-299`); or the `host` role's interface declares its own `serverUrl` and the inventory sets it once as `roles.host.settings.serverUrl` so every host machine inherits it.
Which realization is intended is recorded as Q1 below.

Per-role vars generators.
The `server` role's `perInstance.nixosModule` declares the server-side generators, and the `host` role declares any runner-side generator, each inside the role's own emitted module as `openclaw` and `hermes-agent` do (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/services/openclaw/flake-module.nix:245,256,270,331`, `github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/services/hermes-agent/flake-module.nix:344,360`).
Generator names should embed `instanceName`, as buzz-flake's `buzz-server-${instanceName}` does, because the clan-core option documentation states each per-instance module is produced once per instance and must import cleanly alongside its siblings (`github:fosskar/buzz-flake@6811fbd9bce5a4ec4889d2e6eb48fa75d1a7f4c7:modules/buzz-clan.nix:168-174`, `github:clan-lol/clan-core@1c21a2388ffbf9a957a60f58d18757420666cc43:lib/inventory/distributed-service/service-module.nix:615-630`).

Package ownership.
Neither existing clan service uses `lib.mkPackageOption`; `openclaw` declares `options.services.openclaw.package` by hand inside its per-instance module and `hermes-agent` defers to upstream (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/services/openclaw/flake-module.nix:234-239`, `github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/services/hermes-agent/flake-module.nix:453`).
To satisfy the charter's `mkPackageOption` rule in O2, the emitted module declares `options.services.omnigent.package = lib.mkPackageOption pkgs "omnigent" { }` and `options.services.omnigent-host.package = lib.mkPackageOption pkgs "omnigent" { }`, and the role modules read `config.services.omnigent.package` and `config.services.omnigent-host.package` respectively.
Because option declarations collide if the same option is declared twice on one machine, and `perInstance` modules are produced once per instance, the declarations belong in `perMachine.nixosModule`, which is produced once per machine (`github:clan-lol/clan-core@1c21a2388ffbf9a957a60f58d18757420666cc43:lib/inventory/distributed-service/service-module.nix:714-718,779-801`), or the service is documented as single-instance the way `openclaw` implicitly is.
When `magnetite` holds both roles, both package options default to one `pkgs.omnigent` store path and neither role adds the package to `environment.systemPackages`, so no double install occurs.

Maintenance cost relative to `openclaw` and `hermes-agent`.
O2 reuses the exact file layout, `clan.modules.<name>` binding, `interface`/`perInstance` structure, inline generator declaration, and `module.input = "self"` inventory binding of both existing services, so a maintainer of those files needs no new concept (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/services/openclaw/flake-module.nix:3-19,110-113`, `github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/inventory/services/hermes-agent.nix:2-8`).
It exceeds both in three respects: two roles instead of one, which neither existing service has; cross-role settings access through the `roles` argument if the server URL is derived, which only buzz-flake demonstrates (`github:fosskar/buzz-flake@6811fbd9bce5a4ec4889d2e6eb48fa75d1a7f4c7:modules/buzz-clan.nix:267-274`); and a `darwinModule` branch if `stibnite` joins, which no vanixiets service has and which cannot borrow the Moshi `isDarwin`/`isLinux` split because clan-core separates the two module classes at the result level rather than inside one module (`github:clan-lol/clan-core@1c21a2388ffbf9a957a60f58d18757420666cc43:lib/inventory/distributed-service/service-module.nix:1162-1176`).
It is cheaper than `hermes-agent` in one respect: there is no upstream module and no `environmentFiles` adapter, so the role module authors its own units as `openclaw` does (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/services/hermes-agent/flake-module.nix:143-147,270`).
Package ownership through `mkPackageOption` is a departure from both existing services, and the `perMachine` placement needed to make it collision-safe is a clan-core surface neither existing service uses (`github:clan-lol/clan-core@1c21a2388ffbf9a957a60f58d18757420666cc43:lib/inventory/distributed-service/service-module.nix:714-718`).
Option inspection paths are unchanged from O1 because the role modules still define `services.omnigent.*` on the machine, but the enablement source moves from the machine file to `modules/clan/inventory/services/omnigent.nix`, so a reader of `magnetite/default.nix` no longer sees Omnigent there.
Inventory settings are static literals with no `config.*` visibility, which the repository already documents as a cost it pays for `hermes-agent` and `openclaw` (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/inventory/services/hermes-agent.nix:14-20`, `github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/services/openclaw/flake-module.nix:65-72`); for Omnigent this means the domain or server URL, the port, and any Kanidm issuer URL typed into the inventory cannot be derived from `config.services.kanidm.*` or `config.services.nginx.*`, although the role's emitted `nixosModule` itself is an ordinary module with full `config` access (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/services/openclaw/flake-module.nix:113-124`).
The Buzz self-hosting note at `main` applied exactly this reasoning to a magnetite service and chose the plain module (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:docs/notes/development/buzz/self-hosting.md:282-284`); whether that note binds this decision is Q6.

### Observation common to both options

Buzz-flake's clan `server` role is a thin adapter that imports the flake's own plain NixOS module and forwards settings into it (`github:fosskar/buzz-flake@6811fbd9bce5a4ec4889d2e6eb48fa75d1a7f4c7:modules/buzz-clan.nix:161-172,232-259`).
Neither `openclaw` nor `hermes-agent` is layered that way over a vanixiets-owned plain module; `openclaw` authors everything inside the role and `hermes-agent` wraps an external input (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/services/openclaw/flake-module.nix:113-124`, `github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/clan/services/hermes-agent/flake-module.nix:166`).
The buzz layering means O2's role modules could import O1's `flake.modules.nixos.omnigent` and `flake.modules.nixos.omnigent-host` rather than re-authoring them, which would make O1 a strict subset of O2 rather than an alternative; whether that hybrid is in scope is recorded as Q3.
