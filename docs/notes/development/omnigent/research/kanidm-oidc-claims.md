## 2. Claims Kanidm places in the `id_token` and at userinfo

The `id_token` is built only when the granted scopes contain `openid`, `let id_token = if scopes.contains(OAUTH2_SCOPE_OPENID)` (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:2016`).
Its standard claims are computed by `s_claims_for_account(o2rs, &account, &scopes)` and its custom claims by `extra_claims_for_account(&account, &o2rs.claim_map, &scopes)` (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:2039-2040`).
The userinfo endpoint calls the same two functions on the same account with the scopes stored in the access token, so the `id_token` payload and the userinfo document carry the same claim set (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:3045-3046`; `github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:3050-3066`).

`sub` is the account UUID: the `id_token` sets `sub: OidcSubject::U(session_ctx.account_uuid)` (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:2044`) and userinfo sets `sub: OidcSubject::U(sub)` from the access token's `sub` (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:3052`).
`OidcSubject` is `#[serde(untagged)]` with variants `U(Uuid)` and `S(String)`, so the UUID serialises as a bare hyphenated string (`github:kanidm/compact-jwt@95a3eb9cbc9e9c3272a18ed243ee75d08c291f4e:src/oidc.rs:34-43`).
The unit test asserts `oidc.sub == OidcSubject::U(UUID_TESTPERSON_1)` and that `sub` is identical between the `id_token` and userinfo (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:5785`; `github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:5823`).
The SPN never appears in `sub`.

`email` and `email_verified` are set together and only under the `email` scope:

```rust
let (email, email_verified) = if scopes.contains(OAUTH2_SCOPE_EMAIL) {
    if let Some(mp) = &account.mail_primary {
        (Some(mp.clone()), Some(true))
    } else {
        (None, None)
    }
} else {
    (None, None)
};
```

(`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:3351-3359`).
So `email_verified` is emitted as boolean `true` whenever the `email` scope is granted and the account has a primary mail address, and it is otherwise absent; Kanidm never emits `email_verified: false`.
`OAUTH2_SCOPE_EMAIL` is the string `"email"` via `ATTR_EMAIL` (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:proto/src/constants.rs:259`; `github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:proto/src/constants.rs:118`).
Both fields on `OidcClaims` carry `#[serde(skip_serializing_if = "Option::is_none")]`, so a `None` is omitted from the JSON rather than serialised as `null` (`github:kanidm/compact-jwt@95a3eb9cbc9e9c3272a18ed243ee75d08c291f4e:src/oidc.rs:67-72`).
`account.mail_primary` is `get_ava_mail_primary(Attribute::Mail)` on the entry (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/account.rs:129-131`), which returns the `primary` string of the `mail` value set when that set is non-empty (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/entry.rs:2891-2894`; `github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/valueset/address.rs:562-568`).
The mail value set stores a `primary: String` and a `set: BTreeSet<String>` and no per-address verification state, so "verified" in Kanidm means only that the address is on the account (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/valueset/address.rs:256-259`).
The consent screen lists `email` and `email_verified` as the PII released when `openid` is requested and `email` is granted (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:2608-2614`).

`preferred_username` is `account.name()` when `prefer_short_username` is set and `account.spn()` otherwise, and it is emitted regardless of the `profile` scope (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:3345-3349`).
`name` is always the account `displayname` (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:3372`).
The only claim gated on `profile` is `updated_at` (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:3361-3369`).
The granted scope list itself is emitted as a `scopes` claim (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:3373`; `github:kanidm/compact-jwt@95a3eb9cbc9e9c3272a18ed243ee75d08c291f4e:src/oidc.rs:58-60`).
The unit test for a `prefer_short_username = false` client asserts `preferred_username == Some("testperson1@example.com")` and `name == Some("Test Person 1")` (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:5802-5806`).
For the deployed domain `accounts.scientistexperience.net` (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/nixos/kanidm.nix:46`) an SPN would be `<name>@accounts.scientistexperience.net`, which is not a mailbox; with `preferShortUsername = true` the claim is the bare `<name>`.

`groups` is a custom claim added by `extra_claims_for_account` when any of `groups`, `groups_uuid`, `groups_name`, or `groups_spn` is in the granted scopes; the `groups` scope implies UUID plus SPN, and the claim is one flat array over the account's groups of the requested attribute forms (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:3433-3466`; `github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:proto/src/constants.rs:261-264`).
Claim-map claims are inserted first and the `ssh_publickeys` and `groups` scope claims second "so that a user can't stomp our claim names" (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:3394-3431`).
The `id_token` also carries `auth_time` from the session, `nbf`, `azp`, and `jti` (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:2042-2058`).
The book's tip lists these scope-to-claim relationships and qualifies that "It is not guaranteed that all of the associated claims will be added" (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:book/src/integrations/oauth2.md:220-233`); the source above is the exact rule behind that qualifier.
The discovery document sets `claims_supported = None` (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:3170-3171`), which is why the deployed synapse discovery document, fetched 2026-09-06, carries no `claims_supported` key and cannot by itself answer the `email_verified` question.

## 3. How `scopeMaps`, `supplementaryScopeMaps`, and `claimMaps` reach the consumer

The NixOS module serialises `cfg.provision.{groups,persons,systems}` to JSON (`github:NixOS/nixpkgs@85f62611fa3f3eacbcfe3bc7a6d6518b443ca442:nixos/modules/services/security/kanidm.nix:150-152`) and runs `kanidm-provision --url <instanceUrl> --state <json>` as the idm_admin after the server is up (`github:NixOS/nixpkgs@85f62611fa3f3eacbcfe3bc7a6d6518b443ca442:nixos/modules/services/security/kanidm.nix:239-244`).
`kanidm-provision` is `oddlama/kanidm-provision` at `version = "1.3.0"` (`github:NixOS/nixpkgs@85f62611fa3f3eacbcfe3bc7a6d6518b443ca442:pkgs/by-name/ka/kanidm-provision/package.nix:11-18`), whose tag `v1.3.0` resolves to commit `139c2762e77e10cb2327d76f2f8d99e91e4cb07b`.
`scopeMaps` is "Maps kanidm groups to returned oauth scopes" of type `attrsOf (listOf str)` keyed by group name (`github:NixOS/nixpkgs@85f62611fa3f3eacbcfe3bc7a6d6518b443ca442:nixos/modules/services/security/kanidm.nix:668-675`), and `supplementaryScopeMaps` is "Maps kanidm groups to additionally returned oauth scopes" (`github:NixOS/nixpkgs@85f62611fa3f3eacbcfe3bc7a6d6518b443ca442:nixos/modules/services/security/kanidm.nix:677-684`).
The provisioner writes each `scopeMaps.<group>` entry to the Kanidm attribute `oauth2_rs_scope_map` through `/v1/oauth2/<client>/_scopemap/<group>` and each `supplementaryScopeMaps.<group>` entry to `oauth2_rs_sup_scope_map` through `/v1/oauth2/<client>/_sup_scopemap/<group>` (`github:oddlama/kanidm-provision@139c2762e77e10cb2327d76f2f8d99e91e4cb07b:src/main.rs:255-275`; `github:oddlama/kanidm-provision@139c2762e77e10cb2327d76f2f8d99e91e4cb07b:src/client.rs:248-297`; `github:oddlama/kanidm-provision@139c2762e77e10cb2327d76f2f8d99e91e4cb07b:src/client.rs:18`).

On the server, `process_requested_scopes_for_identity` computes `available_scopes` as the union of `scope_maps` entries for groups the identity is a member of and returns `Oauth2Error::AccessDenied` with the log line `Identity does not have access to the requested scopes` when the requested scopes are not a subset of that union (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:3487-3503`).
The granted scopes are the requested scopes plus every `sup_scope_maps` entry for the identity's groups, so supplementary scopes are added to the token without being part of the admission test (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:3505-3514`).
The book states the same two rules: "For an authorisation to proceed, all scopes requested by the client must be available in the final scope set that is granted to the account", and supplemental scopes "are NOT consulted during authorisation decisions made by Kanidm" (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:book/src/integrations/oauth2.md:296-306`).
So `scopeMaps.omnigent_users = [ "openid" "profile" "email" ]` means an account outside `omnigent_users` cannot satisfy Omnigent's request for `openid email profile` and is refused before any token is issued; this is the group-based admission lever D4 relies on.
The book adds that an OIDC client "**MUST** provide a scope map containing `openid`" (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:book/src/integrations/oauth2.md:243`), which matches the `openid` gate on `id_token` issuance in section 2.
`scopes_supported` in discovery is the union of all scope-map and supplementary-scope-map values (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:982-987`), which is why the deployed synapse document publishes exactly `["email", "openid", "profile"]`.
The NixOS module asserts that every group named in `scopeMaps`, `supplementaryScopeMaps`, and `claimMaps.<claim>.valuesByGroup` is a declared group (`github:NixOS/nixpkgs@85f62611fa3f3eacbcfe3bc7a6d6518b443ca442:nixos/modules/services/security/kanidm.nix:883-898`), which is why `matrix_users` is declared as a stub with `members = [ ]` and `overwriteMembers = false` (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/nixos/kanidm.nix:167-181`).

A group name reaches the consumer by one of three routes.
Route one is the `groups`, `groups_name`, or `groups_spn` scope from section 2, which needs the scope to appear in a scope map or supplementary scope map and in the client's requested scopes.
Route two is `claimMaps`, which "Adds additional claims (and values) based on which kanidm groups an authenticating party belongs to" with `joinType` one of `array`, `csv`, `ssv` and `valuesByGroup` mapping group names to claim values (`github:NixOS/nixpkgs@85f62611fa3f3eacbcfe3bc7a6d6518b443ca442:nixos/modules/services/security/kanidm.nix:692-722`); the provisioner writes these to `oauth2_rs_claim_map` through `/v1/oauth2/<client>/_claimmap/<claim>/<group>` and the join type through `/v1/oauth2/<client>/_claimmap/<claim>` (`github:oddlama/kanidm-provision@139c2762e77e10cb2327d76f2f8d99e91e4cb07b:src/client.rs:299-394`), and the server inverts the stored map into a per-group lookup at reload and merges values per claim name at token time (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:875-916`; `github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:3394-3417`).
The provisioner README's example uses a claim named `groups` with `valuesByGroup` producing values such as `user` and `important_user`, and warns that `removeOrphanedClaimMaps` deletes claim maps the tool did not create because "claim maps are not a separate entity in kanidm" (`github:oddlama/kanidm-provision@139c2762e77e10cb2327d76f2f8d99e91e4cb07b:README.md:68-71`; `github:oddlama/kanidm-provision@139c2762e77e10cb2327d76f2f8d99e91e4cb07b:README.md:217-235`).
The nixpkgs provisioning test exercises exactly this shape, `supplementaryScopeMaps.service1-admin = [ "admin" ]` plus `claimMaps.groups.valuesByGroup.service1-admin = [ "admin" ]`, and asserts `oauth2_rs_claim_map: groups:.*"admin"` on the server (`github:NixOS/nixpkgs@85f62611fa3f3eacbcfe3bc7a6d6518b443ca442:nixos/tests/kanidm-provisioning.nix:105-118`; `github:NixOS/nixpkgs@85f62611fa3f3eacbcfe3bc7a6d6518b443ca442:nixos/tests/kanidm-provisioning.nix:404-406`).
Route three is admission by scope map alone, where the group never appears in a claim and the consumer learns only that the authorisation succeeded; this is the route the synapse client uses today and the only route Omnigent can consume (section 4).

## 4. What Omnigent does with the claims

Omnigent's OIDC configuration is built once at startup by `OIDCConfig.from_env`; `_require` reads and strips `OMNIGENT_OIDC_ISSUER`, `OMNIGENT_OIDC_CLIENT_ID`, `OMNIGENT_OIDC_CLIENT_SECRET`, and `OMNIGENT_OIDC_COOKIE_SECRET`, and the redirect URI is `OMNIGENT_OIDC_REDIRECT_URI` or `https://<OMNIGENT_DOMAIN>/auth/callback` (`github:omnigent-ai/omnigent@381bf638fb31e6a51990d9dab54ea9ef4b933711:omnigent/server/oidc.py:243-278`).
The scope string is `OMNIGENT_OIDC_SCOPES` or the default `openid email profile` (`github:omnigent-ai/omnigent@381bf638fb31e6a51990d9dab54ea9ef4b933711:omnigent/server/oidc.py:359`), and the identity claim name is `OMNIGENT_OIDC_EMAIL_CLAIM` or `email` (`github:omnigent-ai/omnigent@381bf638fb31e6a51990d9dab54ea9ef4b933711:omnigent/server/oidc.py:317`).
The complete set of `OMNIGENT_OIDC_*` names in Python sources at the pin is `ALLOWED_DOMAINS`, `ALLOWED_DOMAINS_PATH`, `ALLOW_INVITES`, `CLIENT_ID`, `CLIENT_SECRET`, `COOKIE_SECRET`, `EMAIL_CLAIM`, `ISSUER`, `LOGOUT_REDIRECT_URI`, `REDIRECT_URI`, `SCOPES`, `SESSION_TTL_HOURS`, and `SKIP_EMAIL_VERIFICATION`, per `git grep -hoE 'OMNIGENT_OIDC_[A-Z_]+' 381bf638fb31e6a51990d9dab54ea9ef4b933711 -- 'omnigent/*.py' | sort -u`; the two that govern scopes and claim names are `OMNIGENT_OIDC_SCOPES` and `OMNIGENT_OIDC_EMAIL_CLAIM`.
The callback validates the `id_token` against the discovery `jwks_uri` with `audience=config.client_id` and `issuer=config.issuer`, accepting `RS256`, `RS384`, `RS512`, `ES256`, `ES384`, `ES512` (`github:omnigent-ai/omnigent@381bf638fb31e6a51990d9dab54ea9ef4b933711:omnigent/server/routes/auth.py:847-882`).
The JWKS lookup is `jwt.PyJWKClient(config.jwks_uri).get_signing_key_from_jwt(id_token)`, which selects the key by the token header's `kid` (`github:omnigent-ai/omnigent@381bf638fb31e6a51990d9dab54ea9ef4b933711:omnigent/server/routes/auth.py:871-872`); Kanidm's ES256 signer embeds `kid` in the protected header by default (`github:kanidm/compact-jwt@95a3eb9cbc9e9c3272a18ed243ee75d08c291f4e:src/crypto/es256.rs:213-220`; `github:kanidm/compact-jwt@95a3eb9cbc9e9c3272a18ed243ee75d08c291f4e:src/crypto/es256.rs:113`) and the deployed synapse JWKS publishes one `EC`/`P-256`/`ES256` key with a `kid` (fetched 2026-09-06).
It then reads `claims.get(config.email_claim)` and rejects a missing or empty value with the log line `Rejecting id_token: %r claim is missing or not a non-empty string (claims present: %s)` (`github:omnigent-ai/omnigent@381bf638fb31e6a51990d9dab54ea9ef4b933711:omnigent/server/routes/auth.py:958-968`).
When the claim name is the default `email`, it requires `_claim_is_verified_true(claims.get("email_verified"))`, which is true only for boolean `True` or the string `"true"` in any case (`github:omnigent-ai/omnigent@381bf638fb31e6a51990d9dab54ea9ef4b933711:omnigent/server/routes/auth.py:842-844`; `github:omnigent-ai/omnigent@381bf638fb31e6a51990d9dab54ea9ef4b933711:omnigent/server/routes/auth.py:999`).
When `email_verified` is `false`, absent, or any other value and `OMNIGENT_OIDC_SKIP_EMAIL_VERIFICATION` is unset, the resolver logs `Rejecting id_token: email %r present but email_verified is not true` and returns `None` (`github:omnigent-ai/omnigent@381bf638fb31e6a51990d9dab54ea9ef4b933711:omnigent/server/routes/auth.py:1007-1011`), and the callback answers `400 {"error": "Could not determine user email from IdP"}` (`github:omnigent-ai/omnigent@381bf638fb31e6a51990d9dab54ea9ef4b933711:omnigent/server/routes/auth.py:337-341`).
When the waiver is set, the same condition logs `Accepting id_token email %r without email_verified (OMNIGENT_OIDC_SKIP_EMAIL_VERIFICATION is set)` and proceeds (`github:omnigent-ai/omnigent@381bf638fb31e6a51990d9dab54ea9ef4b933711:omnigent/server/routes/auth.py:1000-1006`); startup also logs a warning that "Any signed email claim from %s will be trusted as the user's identity" (`github:omnigent-ai/omnigent@381bf638fb31e6a51990d9dab54ea9ef4b933711:omnigent/server/oidc.py:304-312`).
A non-default `OMNIGENT_OIDC_EMAIL_CLAIM` such as `preferred_username` always requires the waiver because `email_verified` vouches only for `email` (`github:omnigent-ai/omnigent@381bf638fb31e6a51990d9dab54ea9ef4b933711:omnigent/server/routes/auth.py:976-992`), and with `preferShortUsername = true` that claim would be a bare account name without `@`, so `is_admitted` would compute an empty domain and deny it whenever any allowed domain is configured (`github:omnigent-ai/omnigent@381bf638fb31e6a51990d9dab54ea9ef4b933711:omnigent/server/oidc_access.py:116-127`).
The identity is lowercased, an invite is redeemed if present, admission is by domain allowlist, admin list, or invite, and admin promotion comes only from the file-backed roster because "the IdP doesn't tell us who is an operator" (`github:omnigent-ai/omnigent@381bf638fb31e6a51990d9dab54ea9ef4b933711:omnigent/server/routes/auth.py:374-415`; `github:omnigent-ai/omnigent@381bf638fb31e6a51990d9dab54ea9ef4b933711:omnigent/server/oidc_access.py:9-30`; `github:omnigent-ai/omnigent@381bf638fb31e6a51990d9dab54ea9ef4b933711:omnigent/server/admin_list.py:1-23`).
`git grep -n -E 'userinfo_endpoint|preferred_username|"name"|groups|roles|"sub"'` over `oidc.py`, `oidc_access.py`, `routes/auth.py`, and `admin_list.py` at the pin matches only docstrings, the `OIDCConfig.userinfo_endpoint` field, and an unrelated `"sub": user_id` in the session cookie minter (`github:omnigent-ai/omnigent@381bf638fb31e6a51990d9dab54ea9ef4b933711:omnigent/server/oidc.py:78`), so Omnigent reads no `name`, `preferred_username`, `groups`, or role claim, calls no userinfo endpoint on the generic OIDC path, and uses only the `id_token`.
The `userinfo_endpoint` is stored from discovery but the docstring states it is for "providers that don't issue `id_token` (GitHub)" (`github:omnigent-ai/omnigent@381bf638fb31e6a51990d9dab54ea9ef4b933711:omnigent/server/oidc.py:159-161`; `github:omnigent-ai/omnigent@381bf638fb31e6a51990d9dab54ea9ef4b933711:omnigent/server/oidc.py:395`).
Consequently Kanidm route one and route two from section 3 would be ignored by Omnigent, and RK3 stands confirmed as the current plan states.
The `.env.example` documents the waiver as the fix when an IdP omits the claim and login "fails ... with 'Could not determine user email'" (`github:omnigent-ai/omnigent@381bf638fb31e6a51990d9dab54ea9ef4b933711:deploy/docker/.env.example:171-177`).

Putting sections 2 and 4 together: with the D4 client and an operator account that has a primary mail address, Kanidm's `id_token` carries `email` and `email_verified: true`, Omnigent's default gate passes, and `OMNIGENT_OIDC_SKIP_EMAIL_VERIFICATION` is not needed.
The one failure mode is an account with no `mail` attribute, for which Kanidm omits both claims and Omnigent rejects with the `'email' claim is missing` log line rather than the `email_verified is not true` line; the fix is `kanidm person update <name> --mail <addr>`, not the waiver.

Omnigent's optional `reauth=1` login path sends `prompt=login` and `max_age=0` and then requires an `auth_time` claim newer than the demand (`github:omnigent-ai/omnigent@381bf638fb31e6a51990d9dab54ea9ef4b933711:omnigent/server/routes/auth.py:180-219`; `github:omnigent-ai/omnigent@381bf638fb31e6a51990d9dab54ea9ef4b933711:omnigent/server/routes/auth.py:343-372`).
Kanidm treats `prompt=login` as `max_age = Some(0)`, forces re-authentication when `max_age <= 0`, and emits `auth_time` from the identity's last verification time in the `id_token` (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:2461-2477`; `github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:2049`), and the unit test asserts `oidc.auth_time.is_some()` (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:5791`), so the reauth path is also satisfiable.

A tag-to-pin diff shows that of `omnigent/server/oidc.py`, `omnigent/server/oidc_access.py`, `omnigent/server/routes/auth.py`, `omnigent/server/admin_list.py`, and `omnigent/server/auth.py`, only `routes/auth.py` changed between `v0.12.0` and the pin (`git diff --stat v0.12.0 381bf638fb31e6a51990d9dab54ea9ef4b933711 -- <paths>` prints `1 file changed, 119 insertions(+), 20 deletions(-)`).
That diff extracts the JWKS validation into `_validate_id_token`, adds the `reauth=1` path above, and leaves the `email` and `email_verified` handling unchanged (`github:omnigent-ai/omnigent@381bf638fb31e6a51990d9dab54ea9ef4b933711:omnigent/server/routes/auth.py:847-882`; `github:omnigent-ai/omnigent@381bf638fb31e6a51990d9dab54ea9ef4b933711:omnigent/server/routes/auth.py:885-913`).
This answers the implementation-time check that plan Q1 asked for: D4 as written applies to `v0.12.0`.

## 5. PKCE, signing algorithm, and client authentication

Omnigent sends `code_challenge_method: S256` unconditionally in the authorization request (`github:omnigent-ai/omnigent@381bf638fb31e6a51990d9dab54ea9ef4b933711:omnigent/server/routes/auth.py:206-214`).
Kanidm accepts only `S256` when a PKCE request is present, `if pkce_request.code_challenge_method != CodeChallengeMethod::S256 { ... return Err(Oauth2Error::InvalidRequest) }` (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:2410-2414`), and requires a challenge when `require_pkce()` is true (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:2416-2418`).
For a confidential (`Basic`) client `require_pkce()` is `enable_pkce`, which is the negation of `oauth2_allow_insecure_client_disable_pkce` defaulting to `true`; public clients always require PKCE (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:733-736`; `github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:573-578`).
The discovery document publishes `code_challenge_methods_supported = [S256]` when PKCE is required and an empty list otherwise (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:3174-3178`); the deployed synapse document shows `["S256"]` (fetched 2026-09-06).
`allowInsecureClientDisablePkce` ("Disable PKCE on this oauth2 resource server to work around insecure clients", `github:NixOS/nixpkgs@85f62611fa3f3eacbcfe3bc7a6d6518b443ca442:nixos/modules/services/security/kanidm.nix:652-660`) therefore stays at its default `false` for the omnigent client.

The signing algorithm is `Rs256` when `oauth2_jwt_legacy_crypto_enable` is true and `Es256` otherwise (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:918-941`), the `id_token` is signed with that one algorithm (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:2068-2071`), and discovery publishes the single matching `id_token_signing_alg_values_supported` value (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:3158-3161`).
`ES256` is in Omnigent's accepted list (`github:omnigent-ai/omnigent@381bf638fb31e6a51990d9dab54ea9ef4b933711:omnigent/server/routes/auth.py:876`), so `enableLegacyCrypto` ("Allows JWT signing algorthms like RS256", `github:NixOS/nixpkgs@85f62611fa3f3eacbcfe3bc7a6d6518b443ca442:nixos/modules/services/security/kanidm.nix:646-650`) stays at its default `false`; the book notes that in legacy mode "Kanidm will not offer `ES256` support for the client at all" (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:book/src/integrations/oauth2.md:408-415`).
The omnigent client is confidential, so `public` stays `false` and `basicSecretFile` is allowed; the module forbids `basicSecretFile` and `allowInsecureClientDisablePkce` on public clients and `enableLocalhostRedirects` on non-public clients (`github:NixOS/nixpkgs@85f62611fa3f3eacbcfe3bc7a6d6518b443ca442:nixos/modules/services/security/kanidm.nix:907-927`).

Omnigent authenticates the token exchange with `client_id` and `client_secret` in the POST body, not an HTTP Basic header (`github:omnigent-ai/omnigent@381bf638fb31e6a51990d9dab54ea9ef4b933711:omnigent/server/routes/auth.py:288-306`).
Kanidm's token endpoint deserialises the form as `AccessTokenRequest`, which flattens a `ClientPostAuth { client_id, client_secret }` (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/core/src/https/oauth2.rs:452-456`; `github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:proto/src/oauth2.rs:192-201`; `github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:proto/src/oauth2.rs:326-329`), and `get_client_auth` uses the Basic header when present and otherwise falls through to the POST-body pair (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:676-690`).
The secret is then compared in constant time against the client's `oauth2_rs_basic_secret` (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:1226-1243`), and discovery advertises both `client_secret_basic` and `client_secret_post` (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:3164-3167`), so Omnigent's `client_secret_post` form works against 1.11.0 and the book's requirement list naming only "HTTP basic authentication" (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:book/src/integrations/oauth2.md:20-22`) is narrower than the implementation.

The synapse client today sets `displayName`, `originUrl`, `originLanding`, `imageFile`, `preferShortUsername = true`, `scopeMaps.matrix_users = [ "openid" "profile" "email" ]`, and `basicSecretFile`, and leaves `public`, `enableLegacyCrypto`, `allowInsecureClientDisablePkce`, `enableLocalhostRedirects`, `supplementaryScopeMaps`, and `claimMaps` at their defaults (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/nixos/kanidm.nix:183-212`).
The synapse consumer requests the same three scopes with `pkce_method = "always"` and maps `preferred_username`, `name`, and `email` into the Matrix account (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/nixos/matrix.nix:300-320`), which matches the always-emitted `preferred_username` and `name` and the `email`-scoped `email` claim from section 2.

## 6. Discovery URL and issuer string

Kanidm registers the routes `/oauth2/openid/{client_id}/.well-known/openid-configuration`, `/oauth2/openid/{client_id}/userinfo`, and `/oauth2/openid/{client_id}/public_key.jwk`, plus a `/.well-known/openid-configuration/oauth2/openid/{client_id}` alias (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/core/src/https/oauth2.rs:769-797`).
The issuer is the server origin with path `/oauth2/openid/{client_id}`, `iss.set_path(&format!("/oauth2/openid/{client_id}"))`, and the userinfo and JWKS URLs are built the same way (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:973-980`); the same `o2rs.iss` value is written into the `id_token` `iss` claim and the discovery `issuer` field (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:2000`; `github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:2043`; `github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:3142`).
The origin is `services.kanidm.server.settings.origin = "https://${domain}"` with `domain = "accounts.scientistexperience.net"` (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/nixos/kanidm.nix:46`; `github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/nixos/kanidm.nix:128-130`).
The book lists the same four URL shapes with `:client_id:` (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:book/src/integrations/oauth2.md:52`; `github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:book/src/integrations/oauth2.md:159`; `github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:book/src/integrations/oauth2.md:171`; `github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:book/src/integrations/oauth2.md:183`).
The deployed server confirms the shape for the synapse client: `"issuer": "https://accounts.scientistexperience.net/oauth2/openid/synapse"` with no trailing slash, `"authorization_endpoint": "https://accounts.scientistexperience.net/ui/oauth2"`, `"token_endpoint": "https://accounts.scientistexperience.net/oauth2/token"`, `"userinfo_endpoint": ".../oauth2/openid/synapse/userinfo"`, and `"jwks_uri": ".../oauth2/openid/synapse/public_key.jwk"` (deployed discovery document, fetched 2026-09-06).
`GET https://accounts.scientistexperience.net/oauth2/openid/omnigent/.well-known/openid-configuration` returned `404` on 2026-09-06 because the `omnigent` client is not yet provisioned; the URL becomes live when `systems.oauth2.omnigent` is deployed.
The deployed synapse consumer already uses the issuer form without a trailing slash, `issuer = "https://accounts.scientistexperience.net/oauth2/openid/synapse"` (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/nixos/matrix.nix:304`).
Omnigent builds the discovery URL as `issuer.rstrip("/") + "/.well-known/openid-configuration"` (`github:omnigent-ai/omnigent@381bf638fb31e6a51990d9dab54ea9ef4b933711:omnigent/server/oidc.py:360`) but stores the unmodified `issuer` string in `OIDCConfig` (`github:omnigent-ai/omnigent@381bf638fb31e6a51990d9dab54ea9ef4b933711:omnigent/server/oidc.py:382`) and passes it as `issuer=config.issuer` to `jwt.decode` (`github:omnigent-ai/omnigent@381bf638fb31e6a51990d9dab54ea9ef4b933711:omnigent/server/routes/auth.py:878`).
Omnigent depends on `PyJWT[crypto]>=2.8,<3` (`github:omnigent-ai/omnigent@381bf638fb31e6a51990d9dab54ea9ef4b933711:pyproject.toml:100`), whose issuer check is a string equality against the token's `iss` claim, so `OMNIGENT_OIDC_ISSUER` must be exactly `https://accounts.scientistexperience.net/oauth2/openid/omnigent` with no trailing slash and no `/.well-known/...` suffix; a trailing slash would still discover but every `id_token` would then fail with `id_token validation failed: Invalid issuer` (`github:omnigent-ai/omnigent@381bf638fb31e6a51990d9dab54ea9ef4b933711:omnigent/server/routes/auth.py:880-882`).
The plan's D4 value `OMNIGENT_OIDC_ISSUER=https://accounts.scientistexperience.net/oauth2/openid/omnigent` is therefore the correct form.
The upstream examples `https://accounts.google.com` and `https://your-tenant.okta.com` are base URLs without a trailing slash, consistent with this (`github:omnigent-ai/omnigent@381bf638fb31e6a51990d9dab54ea9ef4b933711:deploy/docker/README.md:156`; `github:omnigent-ai/omnigent@381bf638fb31e6a51990d9dab54ea9ef4b933711:deploy/docker/README.md:167-180`).

## 7. Consequences for D4 and Q2

D4's field-for-field copy of the synapse client is sufficient on the Kanidm side: `openid`, `profile`, and `email` in `scopeMaps.omnigent_users`, `preferShortUsername = true`, `basicSecretFile`, and defaults for every PKCE and crypto flag.
D4's claim that the scope map is the group-based authorisation lever is grounded by `process_requested_scopes_for_identity` returning `AccessDenied` for a non-member (section 3) together with Omnigent reading no group claim (section 4).
`supplementaryScopeMaps` and `claimMaps` have no consumer in Omnigent and should not be added to the omnigent client.
`preferShortUsername` has no effect on Omnigent because it never reads `preferred_username` under the default `OMNIGENT_OIDC_EMAIL_CLAIM`; it is retained only for parity with synapse.
The Kanidm person record must carry a primary mail address, because the `email` claim is Omnigent's identity and Kanidm emits neither `email` nor `email_verified` without one (section 2); the module documents `mailAddresses` as "First given address is considered the primary address" (`github:NixOS/nixpkgs@85f62611fa3f3eacbcfe3bc7a6d6518b443ca442:nixos/modules/services/security/kanidm.nix:566-571`), and the operator's person record is operational, not declared (`github:cameronraysmith/vanixiets@590f75195cc7acbb3926d39397bf860c2c6efc65:modules/nixos/kanidm.nix:26-28`).
Q2 is settled in the affirmative from source: the deployed `1.11.0` emits `email_verified: true` with the `email` scope for any account with a primary mail, so `OMNIGENT_OIDC_SKIP_EMAIL_VERIFICATION` stays unset and the plan's recommendation to leave it unset stands without the conditional "set the waiver only if the callback rejects" clause.
The trust argument behind Omnigent's gate also holds for Kanidm: at domain level 15 the built-in `idm_acp_self_write` grants people self-modification of credentials and keys but not `mail` (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/migration_data/dl15/access.rs:968-1000`), self-write of `mail` is granted only to members of `idm_people_self_mail_write` by `idm_acp_people_self_write_mail` (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/migration_data/dl15/access.rs:908-926`), that group is built with no default members (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/migration_data/dl15/groups.rs:325-332`), and otherwise `mail` is writable by `idm_people_admins` through `idm_acp_people_pii_manage` (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/migration_data/dl15/access.rs:1358-1378`).
So `email_verified: true` from this deployment means "an administrator set this address", which is the property Omnigent's gate exists to protect, as long as no person is added to `idm_people_self_mail_write`.

## Conclusion

The `email_verified` question is settled: Kanidm 1.11.0 emits `email_verified: true` in both the `id_token` and userinfo whenever the `email` scope is granted and the account has a primary mail address, and omits the claim otherwise (`github:cameronraysmith/kanidm@ed10baa494adc1549c2e9e3d750465cc1052a7d1:server/lib/src/idm/oauth2.rs:3351-3359`).
No runtime probe is required to close Q2; the optional confirmation after `systems.oauth2.omnigent` is deployed is one login with `OMNIGENT_OIDC_SKIP_EMAIL_VERIFICATION` unset followed by `journalctl -u omnigent.service | grep 'Rejecting id_token'`, where no output means the gate passed.
If the operator wants to observe the raw claims once, the following read-only sequence prints the `id_token` payload and the userinfo document for the omnigent client; it is not needed to settle Q2.

```sh
# 1. On any machine: build a PKCE pair and open the authorisation URL in a browser as the operator.
CV=$(openssl rand -hex 32)
CC=$(printf '%s' "$CV" | openssl dgst -sha256 -binary | basenc --base64url | tr -d '=')
printf 'https://accounts.scientistexperience.net/ui/oauth2?response_type=code&client_id=omnigent&redirect_uri=https%%3A%%2F%%2Fomni.scientistexperience.net%%2Fauth%%2Fcallback&scope=openid%%20email%%20profile&state=probe&code_challenge=%s&code_challenge_method=S256\n' "$CC"
# 2. After consent the browser lands on https://omni.scientistexperience.net/auth/callback?code=<CODE>&state=probe (a 502 or 404 there is fine); copy <CODE>.
# 3. On magnetite, exchange the code with the provisioned basic secret and print the id_token payload and the userinfo document.
SECRET=$(sudo cat "$(nix eval --raw .#nixosConfigurations.magnetite.config.clan.core.vars.generators.kanidm-oauth2-omnigent.files.secret.path)")
TOK=$(curl -sS -d grant_type=authorization_code -d "code=<CODE>" -d client_id=omnigent -d "client_secret=${SECRET}" \
  -d redirect_uri=https://omni.scientistexperience.net/auth/callback -d "code_verifier=${CV}" \
  https://accounts.scientistexperience.net/oauth2/token)
printf '%s' "$TOK" | python3 -c 'import sys,json,base64; t=json.load(sys.stdin); p=t["id_token"].split(".")[1]; print(json.dumps(json.loads(base64.urlsafe_b64decode(p+"="*(-len(p)%4))),indent=2))'
curl -sS -H "Authorization: Bearer $(printf '%s' "$TOK" | python3 -c 'import sys,json; print(json.load(sys.stdin)["access_token"])')" \
  https://accounts.scientistexperience.net/oauth2/openid/omnigent/userinfo | python3 -m json.tool
```

The token exchange above deliberately uses the POST-body `client_id`/`client_secret` form so that it also exercises the `client_secret_post` path Omnigent uses (section 5).
